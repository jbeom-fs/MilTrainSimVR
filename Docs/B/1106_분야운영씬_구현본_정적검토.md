# 분야 운영 씬 구현본 정적 검토 — 2026-11-06

요청: 사용자가 첨부한 구현보고서와 실제 코드를 대조하고 문제를 보고한다.
기준: 현재 미커밋 TrainingField 신규 코드, 기존 과정 12개 파일 변경, 개별 저장 씬과 구성·검사 코드 읽기. 코드·씬 수정 및 Unity 컴파일·메뉴·Play·Simulator·헤드셋·테스트·빌드는 수행하지 않았다.

**수정본 후속 검토:** 현재 판단은 아래 §9의 순간이동 선택 필터 수정본 재검토를 우선한다. §1~8은 당시 구현본의 검토 이력이다. 보완된 시작 소유권·바닥 앵커·강제 선택 취소·재개 판정·3초 타임아웃·순간이동 요청 잔류를 그대로 미해결로 재배정하지 않는다.

## 1. 판정과 현재 단계

분야별 씬·과정별 StationRoot·환경 분리·단일 XR을 구성하려는 방향은 사용자 요구와 맞는다. 단, 아래 정적 문제 4건이 있어 운영 구현 완료로 기록하지 않는다.

- 보고서대로 씬 생성·갱신 메뉴 코드가 작성된 단계다. `B_FirstAid.unity`는 Git 변경이 없고 `B_CBRN.unity`는 아직 없다.
- 원본 Tutorial 씬을 추가로 열어 과정 구성을 옮기고 저장 없이 닫는 경로, 공용 설정 자동 변경을 하지 않는 구조, XR 참조 재연결·잘못된 참조 검사, 기존 과정별 초기화 재사용은 코드에서 확인했다. 실제 Editor 동작 성공을 뜻하지 않는다.
- 기존 과정의 입력 게이트·일시 보류·중단 초기화 코드 변경은 있다. ‘단계·판정 미변경’ 보고가 중단·계속하기 시 장비 상태 보존을 보장하지는 않는다.

## 2. P1 — 중단 확인만으로 장비 상태가 바뀜

발생 조건: 장비를 잡거나 KD-1 봉투/패드를 꺼내는 중 `교육 중단`을 누른 뒤 `계속하기` 선택.

근거:

- `TrainingFieldCoordinator.cs:209`~213은 Held 설정 뒤 `CancelSelections()`를 호출하고 시간을 멈춘다.
- `TrainingFieldStation.cs:148`~159는 잡고 있는 모든 과정 장비에 `CancelInteractableSelection`을 실행한다. 기존 잡기나 장비 자세를 재개하는 처리는 없다.
- `KD1Equipment.cs:361`~365는 취소 여부를 구분하지 않고 released에 등록한다. `LateUpdate:391`의 `ApplyReleases:489`~506은 Extracting 아이템을 `PlaceInSlot()`으로 수납 위치에 되돌린다. 이 경로는 Held 또는 CourseAllows로 차단되지 않으므로 확인 중에도 발생 가능하다.
- `AedPad.cs:245`~256은 취소된 선택 종료도 미부착 패드를 dynamic 상태로 바꾼다. `AedTutorialStartController.cs:285`~305도 취소된 패드를 GuidingPadPlacement에서 AwaitingPadPickup으로 바꾼다. 계속하기 이후 물리가 재개되면 패드는 낙하한다.

영향: 확인창 취소인데 꺼내던 장비가 되돌아가거나 패드를 다시 집어야 한다. 보고서의 ‘확정 진행과 장비 상태 유지’ 및 요청한 중단 취소 의미와 불일치한다. Time.timeScale=0은 이 선택 종료 콜백과 LateUpdate의 상태 변경을 막지 않는다.

보완 방향: 중단 확인의 일시 보류와 실제 놓기·잡기 취소의 장비 처리 경로를 구분한다. 계속하기는 기존 동작 상태를 보존해야 한다. 중단 확정에서만 과정의 정상 정리·초기화 경로로 들어간다. 단순히 취소 이벤트를 모두 무시하거나 판정을 완화하는 방식은 피한다.

사용자 확인: KD-1 봉투 반쯤 꺼내기 → 중단 확인 → 계속하기, AED 패드 들기 → 같은 순서. 확인 전후 장비 상태·위치·물리·안내 대상을 비교한다. 실행 미확인.

## 3. P2 — 한 과정만 시작하도록 하는 즉시 승인 경로가 없음

발생 조건: 다른 실습 위치의 교육 시작 입력 두 개가 같은 프레임에 들어옴. 양손 XR UI 입력에서 가능한 조건이며 재현은 하지 않았다.

근거:

- `TrainingFieldCoordinator.cs:119`~151은 LateUpdate에서 이미 시작된 과정을 찾아 Active를 결정한다. 두 과정이 진행 중이면 141행에서 오류 로그만 남긴다.
- 다른 과정의 시작 차단은 `ShowStation:176`~181과 `TrainingFieldStation.Show:184`~192의 가림판 표시다.
- 예를 들어 `TourniquetTrainingStart.TryStart:102`~120 및 `KD1TrainingCourse.TryStart:188`~223은 자기 과정의 준비 상태만 확인하며 현장 코디네이터로부터 시작 소유권을 얻지 않는다.

영향: 가림판 갱신 전 두 시작이 수락되면 두 Runner/과정이 모두 진행된다. 오류 로그만으로 이미 시작된 두 번째 과정을 정리하지 않으므로 ‘한 번에 하나’가 보장되지 않는다.

보완 방향: 과정 시작 직전에 현장 소유권을 동기적으로 확보하고, 준비 실패·중단·완료 후 교육 종료·초기화 실패에 맞춰 해제 정책을 정한다. 가림판은 안내·입력 보조로 유지한다. 개별 Tutorial 실행에서는 기존 시작 동작을 유지해야 한다.

## 4. P2 — 수직 재배치 시 K1·보호의의 몸/발은 월드 Y=0을 사용

발생 조건: 새 교육장 모델의 바닥 높이가 달라 StationRoot와 실습 앵커를 Y축으로 옮김.

근거:

- `K1UserAvatar.cs:110`~111의 floorHeight는 월드 높이 값이며 `Solve:303`이 이를 몸 루트 월드 Y로 쓴다.
- `ProtectiveClothingUserBody.cs:164`도 같은 설정이고 `Solve:682`가 월드 Y에 그대로 사용한다.
- 두 원본 Tutorial 씬의 floorHeight는 0이다. TrainingField 구성·재배치 경로에는 바닥 앵커에 맞춰 이 값을 연결하는 처리가 없다.
- `TrainingFieldSetup.cs:1378`~1380은 수평 회전·배율은 확인하지만 Y 이동을 제한하거나 위 바닥 높이 불일치를 검사하지 않는다.

영향: 실습대·안내·장비는 새 높이에 있지만 사용자 몸·발·보호덧신 판정은 기존 바닥 기준으로 풀린다. 평지 XZ 이동·Y 회전에서는 이 항목이 발생하지 않지만, 요구한 ‘위치만 옮기는’ 재배치 지원은 전체적으로 충족하지 못한다.

보완 방향: 배경 모델을 직접 참조하지 않는 실습/바닥 기준 앵커를 사용자 몸의 바닥 기준으로 연결한다. 장비 조작·동작 기준을 바꾸지 말고 실제 선택한 바닥 기준과 몸/착용 판정을 일치시킨다.

## 5. P2 — EntryAnchor 이동이 실제 시작 위치에 반영되지 않음

발생 조건: 교육장 모델 교체 후 EntryAnchor만 새 입구로 옮기고 저장·재구성·실행.

근거:

- `TrainingFieldSetup.EnsureXr:331`~345는 XR Origin 신규 생성 또는 최초 현장 구성일 때만 EntryAnchor 위치·방향을 적용한다.
- 기존 현장 갱신은 XR Origin을 그대로 둔다. 런타임 TrainingField 코드에는 EntryAnchor를 읽어 시작 위치를 적용하는 연결이 없다.
- 검사 `TrainingFieldSetup.cs:1297`~1298은 두 위치를 정보로 출력할 뿐 일치 여부를 판정하지 않는다.

영향: 입구 안내판만 새 입구로 이동하고 사용자는 예전 XR Origin 저장 위치에서 시작한다. 보고서의 ‘EntryAnchor = 시작 위치’ 및 새 모델 재배치 기대와 다르다.

보완 방향: EntryAnchor를 실제 분야 씬 진입 위치의 단일 기준으로 연결한다. 첫 진입과 같은 과정 다시하기를 구분해, 다시하기 때 사용자를 입구로 이동시키지 않는다.

## 6. 현재 필수 결함과 구분할 항목

- 미생성 씬·미실행 구성 메뉴·미등록 빌드 목록은 보고서에 공개된 미완료 단계다. 구성 실패가 재현된 것으로 기록하지 않는다.
- 실습 범위 이탈 처리는 미구현이다. 현재 코드는 이동만으로 완료·중단·다음 과정을 자동 확정하지 않으므로, 범위 이탈 감시 부재 자체를 새 필수 런타임 오류로 확대하지 않는다.
- 거울 카메라 3대 상시 렌더링과 현장 안내판 겹침 가능성은 실기 성능·가독성 확인 항목이다. 정적으로 확정한 성능 실패·UI 겹침이 아니다.
- 기존 실습 Content의 자동 갱신은 없다. 원본 변경이 통합본에 자동 반영되지 않는 보고서 설명은 코드와 일치한다. 이후 배포/유지보수 방법을 별도로 안내할 필요가 있다.

수정 우선순위: 중단 취소의 장비 상태 보존 → 시작 승인/소유권 → 바닥 높이·입구 앵커 재배치 대응 → 사용자 구성 메뉴·통합 동작 확인.

## 7. 4건 수정본 후속 정적 검토

대상: 두 번째 첨부 보고서(‘문제 4건을 코드에서 수정했습니다…’)와 현재 코드. `Assets/B` 수정 파일 24개 및 TrainingField·시작 게이트 신규 코드와 Editor 연결을 확인했다. 첫 보고서 이후 변경만을 분리한 Git 커밋은 없으므로 현 파일·기존 diff·최초 검토 근거를 대조했다. 컴파일·구성 메뉴·Play·Simulator·HMD·테스트·빌드는 실행하지 않았다.

### 7.1 보완 반영 확인

- 중단 확인의 `CancelSelections` 호출이 제거됐다. AED의 보류도 잡힌 패드를 바로 비활성화하지 않는다. KD1/K1/TQ/PB에 개별 Suspended 경로와 입력 기준 재설정이 연결됐다. 따라서 최초 문제였던 ‘확인창을 여는 것만으로 강제 선택 취소’는 코드상 보완됐다. 재개 판정은 §7.2의 별도 잔여다.
- `ITrainingStartGate`와 `TrainingFieldStation`을 통해 여섯 과정의 실제 시작 진입점이 코디네이터에 동기적으로 승인받는다. `TryClaimStart:207`~220에서 owner를 즉시 설정하고 다른 과정 승인을 거절한다. 완료/실행/정리 중 소유권 유지와 정상 시작 대기 복귀 때 해제하는 경로를 확인했다. 개별 Tutorial의 비어 있는 게이트는 기존 시작을 허용한다.
- `FloorAnchor` 생성·기존 배치 보존·K1/보호의 `floorReference` 연결·검사 경로가 있다. 몸 계산은 `FloorY`를 절대 높이로 읽고 비어 있으면 기존 floorHeight를 사용한다. 최초의 고정 Y=0 문제는 코드상 보완됐다.
- 코디네이터의 EntryAnchor/XROrigin 연결과 런타임 진입 배치가 추가됐다. 로컬 설치 패키지 `com.unity.xr.core-utils@f0450cbac8d6/Runtime/XROrigin.cs`의 실제 API 구현도 읽었다. 사용 API는 Origin을 이동·회전시키는 API이며 HMD Transform을 직접 쓰는 경로가 아니다. 다만 지연 추적 경로는 §7.3에 남는다.

### 7.2 P1 잔여 — 보류 중 목표 위치에 둔 손이 재개 직후 수행으로 인정됨

보고서가 제한으로 명시했지만, 이전 수정 요청의 ‘재개 순간 자동 성공 방지’를 충족하지 못한 부분이다.

- PB: `PressureBandageApplication.cs:475`~481은 Suspended 동안 판정만 건너뛴다. 재개 후 `UpdateEndSnap:741`~748은 기존에 잡고 있던 끝부분이 목표 거리 안에 있으면 바로 `AttachEnd()`를 호출한다. 보류 중 손을 목표 안으로 옮겼는지 구분하지 않는다.
- KD-1: `KD1Equipment.IsReadyForSurface:949`~954는 재개 후 CourseAllows가 참이면 현재 착용·추적 상태로 다시 허용한다. `KD1SurfacePractice.Sense:197`~210은 현재 겹침만으로 done을 기록한다. 착용 패드를 보류 중 미완료 영역에 둔 채 계속하기를 누르면 새 접촉 없이 기록될 수 있다.
- K1: `K1MaskWear.Update:214`~217은 Suspended 동안 return만 한다. 재개 후 `TrySnapToFace:515`~525는 현재 얼굴 거리를 읽고 즉시 얼굴 스냅할 수 있다. `DriveStraps:546`~548도 보류 중 머리 뒤로 옮긴 손을 strapping 확인에 사용할 수 있다. 상대 이동량 기준 재설정만으로 이 절대 위치 판정은 해결되지 않는다.

영향: 교육이 멈춰 있는 동안 목표에 손을 두고 계속하기를 누르면 부착·영역 수행·스냅 등의 과정 진행이 생긴다. 장비 강제 취소는 고쳤지만, 보류 중 행동을 재개 후 수행으로 인정하는 경로는 남았다. 실행 재현은 하지 않았다.

보완 방향: 현장 보류에서 복귀하는 경우에 한해 대상·동작별로 새 유효 행동을 기다리는 재무장 상태를 둔다. 예를 들어 보류 중 목표 안에 들어간 대상은 밖으로 나온 뒤 다시 접근하도록 한다. 기존에 확정된 상태는 유지하고, 성공 거리·영역·KD1의 각도/속도 기준이나 개별 Tutorial의 기존 조작을 바꾸지 않는다. 실제 추적 복귀 동작을 이번에 일괄 변경하라는 뜻도 아니다.

사용자 확인 조건: PB 끝을 잡고 보류 → 목표 안으로 이동 → 계속하기, KD1 패드 착용 후 보류 → 미완료 영역에 접촉 → 계속하기. 재개만으로 Stage/DoneCount가 변하면 실패다. K1은 얼굴 스냅과 머리 뒤 손의 확인 시점을 따로 확인한다.

### 7.3 P2 — HMD 추적이 3초보다 늦으면 입구 배치가 임시 자세로 확정됨

발생 조건: 분야 씬을 연 뒤 3초가 지나서 Quest Link/HMD의 유효 위치·회전 추적이 들어옴. 실제 장치 연결 지연에서 가능한 조건이며 이번에 재현하지 않았다.

근거:

- `TrainingFieldCoordinator.Update:163`~167은 추적 성공 또는 3초 경과 중 하나만 충족해도 `PlaceAtEntry`를 실행한다.

- `Start:134`가 초기 Origin을 앵커에 두더라도, 이후 들어오는 HMD의 실제 수평 오프셋·방향이 임시 카메라 자세와 다르면 최종 머리 위치·방향이 앵커 기준과 달라진다.
- 진입 배치 대기 중에도 `TryClaimStart:209`~220에는 entryPlaced 확인이 없다. 보정 전에 실습을 시작할 수 있는 입력 경로도 남아 있다.

영향: 늦게 연결된 실제 HMD에서 요구한 입구 위치·방향이 보장되지 않는다. 추적이 정상적으로 즉시 들어오는 경우의 앵커 연결 보완과 구분한다.

보완 방향: 임시 배치와 실제 추적 기준의 진입 완료를 구분한다. 실제 추적 후 한 번의 배치가 끝나기 전에는 교육 시작을 승인하지 않고 준비 상태를 안내한다. 정상 진입 후 중단·다시하기·교육 종료 또는 일반 추적 복귀마다 사용자를 입구로 이동시키지 않는다.

사용자 확인 조건: 실제 추적이 없는 상태로 씬 진입 → 3초 이상 대기 → 실제 HMD 연결. 머리의 수평 오프셋과 방향이 있는 상태에서 EntryAnchor 기준으로 한 번 정렬되고, 실습 시작 후 추가 입구 이동이 없어야 한다.

### 7.4 남은 실행 확인과 현재 상태

## 8. 재무장·HMD 진입 대기 수정본 재검토

대상: 사용자가 채팅으로 제출한 ‘문제 2건을 코드에서 수정했습니다…’ 보고서와 현재 코드. 신규 현장 코드, 관련 과정의 재무장/초기화, 구성·검사 연결을 읽었다. 설치된 XRI 패키지의 순간이동 요청·Provider 동작도 정적으로 확인했다. Unity 컴파일·메뉴·Play·Simulator·HMD·테스트·빌드는 실행하지 않았다.

### 8.1 이전 2건의 보완 반영

- PB: `PressureBandageApplication.Suspended:247`~259가 보류 해제 시 목표 안의 끝을 재무장한다. `TryPlaceEnd:749`, `UpdateEndSnap:768`이 놓기/잡은 채 부착을 모두 차단한다. 거리 밖 관찰 후 해제, `ClearApplicationState:903`의 초기화, 행동 안내도 연결됐다.
- KD1: `KD1SurfacePractice.LateUpdate:205`~217이 현장 보류 종료를 관찰하고, `RearmTouchedAreas:221`~230이 겹친 미완료 영역만 잠근다. `ReleaseRearmedAreas:233`~251은 양손 착용 패드가 모두 이탈해야 해제하고 `Sense:261`이 기록을 막는다. 완료 영역은 유지하고 장비 초기화 때 rearm 배열을 비운다. holdSeen은 초기화 함수에서 직접 지우지 않지만 다음 LateUpdate에서 비워지며 초기화 직후 착용 패드가 없어 현재 필수 오류로 분류하지 않았다.
- K1: 보류 해제에서 `RearmAfterHold:683`~695 실행. 얼굴 스냅은 기존 해제 거리 밖 관찰까지 차단하고 끈 확인은 손을 앞쪽으로 가져오거나 새 끈 잡기 전까지 막는다. 기존 faceControlled·strapSeating 확정 상태를 보존하며 새 회차에 플래그를 초기화한다. 기존 성공 수치는 변경하지 않았다.
- 입구: `TrainingFieldCoordinator.Update:173`~187은 실제 위치·회전 추적을 기다리며 3초 뒤에는 로그만 남긴다. `TryClaimStart:231`~235가 진입 대기 중 시작을 거절한다. 입구/과정 상태·가림판 문구, 추적 입력 바인딩 검사도 있다. `PlaceAtEntry` 이후 반복 정렬은 하지 않는다.

따라서 §7의 두 문제는 코드상 보완된 상태다. 실행 통과를 뜻하지 않으며 아래의 새 순간이동 대기열 문제를 구분한다.

### 8.2 P2 — 입구 대기 중 순간이동 요청이 남아 진입 직후 실행될 수 있음

발생 조건: HMD 추적을 기다리는 중 컨트롤러로 순간이동 대상을 선택·놓은 뒤, 실제 HMD 추적이 들어옴. 컨트롤러 입력은 가능하지만 HMD 위치·회전 추적이 아직 준비되지 않은 상황의 경로다. 이번에 실행 재현하지 않았다.

근거:

- `TrainingFieldCoordinator.HoldLocomotion:450`~459는 LocomotionProvider 컴포넌트의 enabled만 false로 설정한다. 순간이동 입력·인터랙터·TeleportationArea/Anchor의 요청 생성 경로를 차단하지 않는다.
- 설치 패키지 `Library/PackageCache/com.unity.xr.interaction.toolkit@4612b35e2aac/Runtime/Locomotion/Teleportation/BaseTeleportationInteractable.cs:308`~325는 Provider 존재 여부만 확인하고 `QueueTeleportRequest`를 호출한다. Provider의 enabled를 확인하지 않는다.
- 같은 폴더 `TeleportationProvider.cs:47`~51은 비활성 상태에서도 currentRequest를 저장하고 validRequest=true로 설정한다. 상위 `LocomotionProvider.OnDisable:177`~179는 비어 있으며 대기 요청을 지우지 않는다.
- `TrainingFieldCoordinator.PlaceAtEntry:439`~443은 입구에 정렬한 직후 Provider를 다시 켠다. 그러면 TeleportationProvider.Update에서 남은 validRequest가 실제 위치·방향 변환으로 적용될 수 있다.

영향: 준비 중에는 이동하지 않아도, 준비 완료 직후 입구 정렬에 이어 대기 중 눌렀던 목적지로 다시 이동한다. 보고서의 ‘준비 중 이동 입력 제어’가 요청 유입·잔류까지 보장하지 못한다.

보완 방향: 진입 대기 중에는 현장 소유의 입력/상호작용 경계에서 순간이동 요청이 생성되지 않도록 차단한다. 잠금/해제 경계에 이미 들어온 요청도 진입 완료 후 실행되지 않도록 처리한다. 장비/UI 입력과 HMD 시점 추적은 유지하고, 원래 비활성인 이동 기능을 임의로 켜지 않으며 공용 패키지 원본을 수정하지 않는다. 정상 진입 후 새로 입력한 순간이동은 허용한다.

사용자 확인: HMD 추적 없이 입구 대기 → 컨트롤러 순간이동을 여러 바닥·실습 위치에 요청 → HMD 추적 연결. 입구 정렬 뒤 과거 요청 위치로 이동하면 실패다. 이후 새로 입력한 순간이동은 정상 동작해야 한다.

### 8.3 현재 상태와 검토 한계

- 현재 저장 B_FirstAid 씬 변경 없음, B_CBRN 미생성을 재확인했다. 코드 보완과 운영 씬 생성·실행 성공은 구분한다.
- 기존 C# diff의 공백 검사에서 오류 없음. 컴파일 성공의 근거가 아니다. 사용자가 보고한 괄호 짝 검사도 컴파일 근거로 확대하지 않는다.
- 이번 범위에서 재무장·실제 추적 대기 자체에 추가 필수 오류를 찾지 못했다. K1의 더 넓은 해제 거리, KD1의 추적 없는 패드가 이탈 전까지 재무장을 유지하는 제한은 보고서와 일치한다.
- 코드·씬·자산·패키지 원본은 변경하지 않았다. 검토·진행상황 문서만 갱신했다.

## 9. 순간이동 선택 필터 수정본 재검토

대상: 사용자가 제출한 TrainingFieldCoordinator 한 파일 수정 보고서와 현재 파일, 설치 XRI의 선택/활성/순간이동 요청 코드, Starter Assets 입력 제어·실제 Teleport Interactor 프리팹. Unity 컴파일·메뉴·Play·Simulator·HMD·테스트·빌드는 실행하지 않았다.

### 9.1 현재 결론

**현재 B 운영 씬 구성 경로에서 추가 필수 코드 문제는 발견하지 못했다.** §8.2의 Provider만 꺼 둬 요청이 남는 원인은 선택 필터로 보완됐다. 정적 확인이며 실제 사용자 실행 통과가 아니다.

- `TrainingFieldCoordinator.Start:166`에서 이 씬의 TeleportationArea/Anchor에 필터를 설치한 뒤 Provider를 끈다. `FindObjectsInactive.Include`로 비활성 대상도 포함하고 다른 씬은 제외한다.
- `Process:481`~487이 entryPlaced 전 새 선택을 거절한다. 현재 패키지의 BaseTeleportationInteractable은 선택/활성 이벤트에서 요청을 만들며 Assets 내 직접 QueueTeleportRequest/SendTeleportRequest 호출은 검색되지 않았다.
- 현재 Teleport Interactor 프리팹은 m_AllowHoveredActivate=0이다. 따라서 현재 구성에서는 선택 차단이 활성 이벤트를 통한 요청 유입도 막는다.
- `PlaceAtEntry:469`~471은 진입 완료 직후 눌린 입력을 수집하고 Provider를 복구한다. `HoldPressedTeleportInput:515`~524는 XR Origin 아래 비활성 포함 입력 인터랙터를 살피며, 활성 인터랙터의 논리 또는 실제 select 입력이 눌려 있으면 해제 대기에 넣는다.
- `Update:198`~202에서 입력 해제를 관찰해 대기를 제거한다. `Process`는 대기 인터랙터의 새 선택을 계속 막으며, 이미 시작된 선택은 통과시켜 필터 자체가 놓기 요청을 만들지 않는다.
- 로컬 XRI 실행 순서에서 XRInteractionManager는 -105, 코디네이터는 300이다. 진입 정렬 프레임의 선택 처리는 아직 entryPlaced=false인 상태에서 실행되며, 다음 프레임부터 선택 허용/입력 해제 대기를 적용하는 구조다.
- Starter Assets의 ControllerInputActionManager는 순간이동 입력 해제 시 상호작용 처리가 끝난 뒤 광선을 비활성화한다. 현재 IsSelectReleased의 비활성 해제 조건은 이 기존 동작과 맞는다.
- OnDisable에서 필터·입력 해제 대기를 정리하며, Provider 복원은 기존에 켜져 있던 목록만 사용한다. 장비/UI 선택 필터로 확대하거나 배경·배치를 변경하지 않는다.

### 9.2 보고서 표현과 적용 범위

- 보고서의 ‘활성은 선택이 전제’는 XRI 전체에 대한 보편 규칙으로 일반화하지 않는다. XRBaseInputInteractor는 allowHoveredActivate 설정에서 hover 대상에도 활성 이벤트를 보낼 수 있다. 현재 사용 Teleport Interactor는 이 옵션이 0이고 구성 메뉴의 대상은 기본 선택 해제 트리거이므로 이번 필수 결함으로 배정하지 않는다.
- 실행 중 신규 생성 대상·커스텀 직접 요청 코드에는 필터가 자동 적용되지 않는다. 보고서에 공개된 제한과 일치하며 현재 현장 코드에는 해당 생성/직접 요청 경로를 찾지 못했다. 추후 추가한다면 등록/잠금 계약을 함께 확장해야 한다.
- 이 결론은 정상적인 현재 씬 시작·진입·종료 경로에 대한 것이다. 코디네이터 컴포넌트 수동 비활성화/재활성화를 교육생의 운영 결함으로 확대하지 않는다.
