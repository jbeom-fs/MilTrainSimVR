# KD-1 기본 조작 구현 보고·실제 코드 정적 검토

> **최신 상태:** 슬롯/착용의 Rigidbody 위치 쓰기 제거 수정본은 §21에서 검토했다. 사용자 1사이클 성공 보고와 기존 Editor.log의 시작·4단계·3/3 완료·요약·초기화 후 시작 대기 복귀를 확인했다. 추가 필수 코드 오류는 미발견이다. 두 번째 회차·양손 각각·HMD 전체 검증으로 확대하지 않는다. 사용자는 현재 KD-1의 상단 챕터/단계 제목과 UI/UX를 B 전체 교육 UI 기준으로 지정했다. 다른 과정은 단계 수와 내용에 맞춰 같은 틀을 적용하며 아직 코드는 변경하지 않았다.

기준: 2026-11-05, 사용자가 전달한 구현보고서와 실제 신규 코드. 검토 범위는 `Assets/B/Scripts/Decontamination/KD1/`의 런타임 6개와 asmdef, `Assets/B/Editor/Decontamination/KD1/`의 구성·검사 코드 2개와 asmdef, 로컬 XRI 3.4.1·Input System 소스 및 Starter Assets 설정이다.

코드·모델·씬·설정은 수정하지 않았다. Unity·컴파일·메뉴·Play·Simulator·테스트·빌드를 실행하지 않았으며 검증용 프로젝트도 만들지 않았다. 아래는 실행 재현 결과가 아니라 코드상 경로와 영향이다.

## 1. 결론

확인한 기능 구현은 보고서와 대체로 일치한다. 외포장·패킷·패드의 독립 상태, 추출 축 제한과 슬롯 복귀, Activate 해제 대기, 정상 XRI 선택 종료를 이용한 장착·초기화, 구성 메뉴·읽기 전용 검사·안내 상수는 존재한다.

다만 **자기 착용 패드의 hover가 다른 선택을 가로막는 문제**, **패드 해제 시 착용한 손의 추적을 확인하지 않는 문제**가 남는다. 추가로 **추적/포커스 소실 중 입력 해제 판정을 허용하는 조건부 위험**이 있다. 실행 통과로 표시하지 않는다.

## 2. 높음 — 자기 패드를 hover 후보에서 제외하지 않음

근거:

- `KD1Equipment.cs:155`: `selectFilters`만 등록한다.
- `KD1Equipment.cs:242`: Worn 패드의 같은 손 선택은 select 단계에서만 거절한다.
- `KD1Item.cs:189`: 착용 상태의 잡기 Collider 묶음은 활성 상태다. 반대 손으로 벗기기 위해 필요한 구성이다.
- 로컬 XRI `NearFarInteractor.cs:684`: near 후보는 hover 가능 여부로 모은다.
- 같은 파일 `:520`: 후보를 거리로 정렬하고 `:765`의 `GetValidTargets`는 첫 후보 하나만 전달한다(`m_AllowMultipleValidTargets=false`).
- `XRInteractionManager.cs:879`: hover 판정은 select filter를 사용하지 않는다.
- Starter Assets의 기본 near 반경은 0.1m이며 자기 착용 패드는 손 주변에 남는다.

영향: 패드를 장착한 손으로 다른 패킷·패드나 반대 손의 착용 패드를 잡으려 할 때, 자기 패드가 가장 가까운 hover 후보이면 그것만 전달된다. select 단계에서 자기 패드를 거절해도 다음 후보로 자동 대체되지 않는다. 보고서의 ‘자기 패드 위에 hover 표시가 생길 수 있지만 잡히지는 않음’을 단순 표시 제한으로만 볼 수 없다.

보완 기준: 같은 손의 착용 패드는 해당 손의 후보 수집/hover 단계에서 제외하고, 반대 손에는 제거 대상으로 유지한다. 전역 Collider 비활성으로 양손 모두 못 잡게 만드는 방식은 피한다.

사용자 확인: 한 손 장착 후 그 손으로 가까운 다른 물체 선택, 양손 장착 후 반대 손 패드 선택·해제를 확인한다. 자기 패드 때문에 다른 대상 후보가 사라지면 실패다. 현재 실행 재현은 하지 않았다.

## 3. 중간 — 착용 손 추적이 끊겨도 반대 손으로 해제 가능

근거:

- `KD1Equipment.cs:233`은 새로 잡는 손의 driver만 확인한다.
- `:242`의 Worn 분기는 다른 손인지 확인하며, 착용한 손/마운트 driver의 추적은 확인하지 않는다.
- `:270`에서 바로 `Unfit`으로 들어가고, `:465`의 해제 함수에도 기존 착용 손 추적 확인이 없다.

영향: 왼손 패드 착용 → 왼손 추적 소실 → 추적이 정상인 오른손을 화면에 남은 왼손 패드 위치로 가져가 잡으면 왼손 추적이 없어도 즉시 해제된다. 보고서의 ‘소실 중 장착·해제가 일어나지 않음’ 및 추적 소실 중 새 장착 해제를 확정하지 않는 요구와 다르다.

보완 기준: 착용 패드 해제는 잡는 손과 기존 착용 손의 추적·포커스 유효성을 함께 확인한다. 기존 선택을 갑자기 끊거나 전체 초기화를 요구하는 방식으로 확대하지 않는다.

사용자 확인: 착용 손만 가린 상태에서 반대 손으로 잡아도 해제되지 않아야 하고, 추적 복귀 뒤에는 정상 해제돼야 한다. 현재 실행 재현은 하지 않았다.

## 4. 조건부 위험 — 소실 중 입력의 0을 유효한 해제로 인정

근거:

- `KD1Equipment.cs:391`의 `ArmReleasedTriggers`는 interactor 활성 여부와 `logicalActivateState.active`만 본다. focus·tracking·입력 잠금 검사가 없다.
- `:299`의 LateUpdate는 이 arming 함수를 계속 호출한다. 추적/포커스 소실 시 `armed`를 해제하는 별도 수명주기 처리도 없다.
- 로컬 Input System은 포커스·장치 배경 동작 조건에 따라 입력 장치를 reset/disable하고 복귀 시 동기화할 수 있다(`InputManager.OnFocusChanged`). 이 동작이 모든 XR 장치에서 동일하다는 뜻은 아니다.

조건부 영향: 장치 입력이 소실 중 0으로 초기화되는 환경에서는 이를 실제 트리거 해제로 인정해 재무장할 수 있다. 복귀 때 누르고 있던 트리거가 다시 활성으로 보고되면 새 유효 입력으로 처리될 경로가 있다. `ApplyPress`의 현재 focus·tracking 확인만으로 소실 중 재무장된 사실을 구분할 수 없다.

보완/확인 기준: 소실 시 입력 대기를 해제하고, 유효한 추적·포커스에서 놓임을 확인한 뒤 새 누름을 요구한다. 트리거를 누른 채 포커스/추적 소실·복귀할 때 자동 개봉/장착이 발생하는지 사용자 확인이 필요하다. 실제 장치별 발생 여부는 미확인이다.

- 검토 시작과 종료의 Git 상태에는 신규 Editor/런타임 폴더만 있었다. 기존 파일 변경 없음이라는 보고와 현재 상태는 일치한다. 이번 검토 문서는 그 이후의 Docs/B 변경이다.
- 메뉴가 생성할 씬·Prefab·재질은 코드로 정의돼 있으나 메뉴 미실행 상태를 생성 완료·연결 완료로 기록하지 않는다.

- 설정 검사는 현재 구성 검사다. 자기 hover 후보 경쟁·양손 추적 조건·입력 소실/복귀 동작까지 PASS로 보장하는 검사가 아니다.

## 6. 수정본 후속 정적 검토

사용자는 `KD1Equipment.cs`의 3건 보완과 `KD1Item.cs`의 Worn 선택 거절 경로 보완을 보고했다. 현재 두 파일과 설치된 XRI의 `XRInputButtonReader`·`XRBaseInputInteractor`를 대조했다. 코드·씬·모델은 수정하지 않고 Unity·컴파일·메뉴·테스트를 실행하지 않았다.

### 6.1 기존 보완 반영 확인

- ① `KD1Equipment.cs:179`·`:206`에서 hover filter 등록/해제, `:294`에서 자기 손 Worn 패드 후보 제외를 확인했다. 기존 선택 통과와 반대 손 후보 유지 조건이 있다.
- ② `:308`의 `CanRemove`는 잡는 손과 착용 손의 추적, 손당 소유 관계, 포커스와 잠금을 확인한다. select 분기 `:287`과 상태 전환 전 `:340`에서 공통 사용한다. 거절된 선택은 `:408`에서 정상 취소·마운트 복원하며, `KD1Item.cs:262`는 Worn 상태의 선택 추종을 막는다.
- ③ 포커스/일시정지 통지의 입력 폐기 `:221`, 손별 무효 상태의 armed·validSince·pending 폐기 `:390`, 유효 시간과 해제를 확인한 재무장 `:515`, 이벤트 수집/적용 시 유효성 재확인은 존재한다. 아래 예외 때문에 전체 경로 해결로 단정하지 않는다.
- Inspector에 필터를 추가할 필요 없이 Awake에서 연결되는 구조이며, 초기화 때 필터를 재등록하지 않는다. 이 확인을 컴파일·메뉴·실기 통과로 확대하지 않는다.

### 6.2 중간·조건부 — 실제 누름 판정 Action이 무효여도 입력 유효 통과

`KD1Equipment.IsBound(XRInputButtonReader)`의 `:539`~`:544`는 performed Action **또는** value Action 중 하나만 활성·바인딩돼도 통과한다.

그러나 설치된 XRI `XRInputButtonReader.cs:401`의 `ReadIsPerformed`와 `:436`의 `ReadWasPerformedThisFrame`은 performed Action을 읽으며 value Action으로 대체하지 않는다. `XRBaseInputInteractor.cs:445`~`:446`도 이 결과로 logicalActivateState를 만든다.

조건부 경로: performed Action이 비활성/미바인딩이고 value Action만 활성·바인딩된 경우 → HandInputValid는 true → logicalActivateState는 false → 0.25초 뒤 해제를 인정하고 armed=true. 따라서 ‘누름 입력이 없어 생긴 0을 해제로 인정하지 않음’을 완전히 보장하지 못한다. 이후 performed Action 재활성화가 누른 채인 트리거를 performed로 보고하는 환경이면 새 놓임 없이 입력이 적용될 위험이 남는다.

실제 기본 Quest/Starter Assets 구성에서 이 부분 무효 상태가 발생했다고 재현한 것은 아니다. 특정 장치에서 반드시 자동 개봉된다고 단정하지 않는다. 다만 actual performed 입력이 아닌 value 입력으로 검증을 대신할 수 있다는 코드 경로는 확인됐다.

보완 기준: logicalActivateState의 실제 근거인 performed Action의 enabled·실제 controls를 필수 확인한다. 아날로그 value Action은 별도 용도로 취급하며 누름 소스 유효성을 대체하지 않는다. 두 Action이 모두 있어야 하는 것으로 불필요하게 강화하지 말고 실제 읽기 경로에 맞춘다.

### 6.3 낮음 — 0.25초 대기의 보고 범위 정정

보고서는 ‘잡은 직후나 복귀 직후 0.25초 안의 놓임은 인정하지 않음’이라고 설명했다. 실제 `OnSelectEntered(:325)`는 armed만 해제하고 기존 validSince는 지우지 않는다. `RestoreAll(:749)`도 기존 validSince를 지우지 않는다. 따라서 0.25초는 최초 해당 손 등록/유효성 복귀 기준이며 매 새 잡기·초기화 기준이 아니다.

이 차이를 이유로 모든 잡기에 추가 지연을 넣을 필요는 없다. 기존 ‘잡은 뒤 유효한 놓임을 확인하고 새 누름 요구’ 규칙을 유지하면서 보고 문구를 실제 동작에 맞추면 된다.

### 6.4 기존 제한·현재 확인 범위

- 착용 손 추적 때문에 해제를 거절할 때 별도 안내가 없는 것은 보고서가 명시한 사용성 제한이다. 새로운 핵심 상태 결함으로 재분류하지 않는다.
- Manual/ObjectReference 입력 모드 제외도 현재 Starter Assets 사용 범위에서 확장 미지원 사항이다. 이번 검토로 다른 입력 방식 지원을 추가 요구하지 않는다.
- 0.25초는 입력 안정화용 개발 설정이며 실제 장치의 새 입력 샘플 수신 자체를 증명하는 값은 아니다.
- 다음은 performed 소스 검증의 처리 후 사용자 컴파일 → 메뉴 1·2 → 자기 hover 제외·양손 해제·추적/포커스 복귀·초기화 확인이다. 현재 단계에서 에이전트 실행 검증은 하지 않는다.

## 7. performed 소스 보완 후 재검토

사용자 후속 보고와 현재 `KD1Equipment.cs`, 설치된 XRI 리더·Interactor 소스를 다시 대조했다. 코드 수정·컴파일·메뉴·Unity 실행은 하지 않았다.

- `KD1Equipment.cs:539`의 `IsBound(XRInputButtonReader)`는 InputAction의 `inputActionPerformed`, InputActionReference의 `inputActionReferencePerformed.action`만 확인한다. `:555`에서 존재·enabled·controls를 요구하며 value를 대체 조건이나 필수 조건으로 사용하지 않는다.
- XRI `XRInputButtonReader.ReadIsPerformed`·`ReadWasPerformedThisFrame`도 해당 performed 소스를 읽는다. bypass가 있으면 XRI 읽기 소스가 바뀌므로 현재 KD1 검사는 이를 무효 처리한다. 현재 지원 범위를 넓히지 않은 방식이다.
- 유효성 검사는 무효 입력 폐기·놓임 재무장·Activate 수집·실제 적용의 공통 `HandInputValid` 경로에 연결돼 있다. 기존 value만 유효한 상태의 통과 경로는 제거됐다.
- `:37`부터의 클래스 설명과 `:82`의 상수 주석은 0.25초를 최초 등록/유효성 복귀 기준으로 설명한다. 새 잡기·초기화마다 타이머를 재시작하지 않는 실제 동작과 일치한다. 복귀 후 트리거를 너무 빨리 놓고 다시 누르면 다시 놓고 누를 필요가 있는 기존 제한은 유지된다.

**현재 결론:** 이번 수정 범위에서 추가 필수 수정 오류는 발견하지 못했다. 기존 지적 사항은 코드상 보완 반영으로 정리하며, 컴파일·메뉴·Play·Simulator·헤드셋 통과를 뜻하지 않는다. 현재 남은 것은 사용자 실행 확인과 이미 명시된 입력 모드 제한·착용 손 추적 거절의 안내 부족 등이다. 이 제한들을 새 기능 확장/필수 수정으로 자동 재배정하지 않는다.

## 8. 사용자 메뉴 검사 로그 — 좌표계 오판 34건

사용자 첨부 로그는 끝이 `<message truncated>`로 잘렸으나, 기존 로컬 `Editor.log`의 같은 검사 보고서에서 `Result: 34 FAIL item(s).`와 Scene 절까지 확인했다. 호출 기록은 메뉴 1 Build → Validate이며, KD1 씬·Prefab·재질·모델 meta가 생성된 현재 파일도 존재한다. 검토자가 Unity나 메뉴를 실행한 것은 아니다. 최신 컴파일 전체 결과와 Play·Simulator·헤드셋 결과는 별도 미보고다.

### 8.1 모델 검사 25건 — 모델 로컬 프레임과 Unity 프레임 혼용

`KD1EquipmentSetup.Validate.cs:90`은 `Union(root, …)`로 메시 크기를 FBX 루트 로컬 프레임에서 측정한다. `:103`·`:105`의 앵커도 `root.InverseTransformPoint/Direction`으로 측정해 루트의 축 변환 회전을 제거한다. 반면 기대값은 `:133`의 `ToUnity`로 변환한 Unity 프레임이다. `:97`의 바닥 검사도 해당 로컬 프레임 Y를 높이로 취급한다.

예: 외포장 측정은 루트 로컬에서 200×160×32.9mm, 기대값은 Unity 기준 200×32.9×160mm다. Grip 실측 `(0,0,16.455)`와 기대 `(0,16.455,0)`도 같은 혼용이다. 루트 로컬 Y의 최솟값 −80mm를 바닥 아래로 판정하지만, 이는 포장 깊이의 반쪽 값이다.

현재 크기 6건·바닥 5건·앵커 14건이 이 범주다. 씬의 배치와 Collider 검사는 아이템 프레임에서 각각 200×33×160mm 등으로 통과하고, 작업대 위 바닥 간격도 1mm로 통과했다. 이 로그만으로 실제 모델이 잘못 눕거나 매몰됐다고 판단하지 않는다.

### 8.2 인스턴스 항등 검사 9건 — 구성 코드와 검사 계약 불일치

구성 함수 `KD1EquipmentSetup.cs:519`는 원본 asset의 localPosition/localRotation/localScale을 인스턴스에 적용한다. 반면 검사 `KD1EquipmentSetup.Validate.cs:205`는 모델 자식의 회전을 Quaternion.identity로 요구한다.

현재 생성 Prefab의 모델 인스턴스 회전은 quaternion X≈−0.7071068, W≈0.7071067(약 −90° X)이며 임포트 축 변환을 유지한 값이다. 외포장 1개·패킷 4개·패드 4개가 같은 항등 검사에서 실패했다. 모델 출처·부모·원본 대비 추가 변환 여부를 확인해야 하며, Unity 임포트가 요구한 회전을 강제로 0으로 만들면 안 된다.

### 8.3 다음 수정 범위와 확인 기준

## 11. 보호장갑 두드림 구현 보고·실제 코드 검토

사용자 첨부 `09135a3d-6781-494c-8387-1ab489b93cd0/붙여넣은 텍스트.txt`와 새 `KD1SurfacePractice.cs`·`KD1SurfaceZone.cs`·`KD1EquipmentSetup.Practice.cs`, 변경된 Equipment·Guide·TrainingSubtitles를 읽었다. 기존 모델 meta·씬·Editor 검사 및 Unity 6.3 공식 문서도 대조했다. 이번 작업에서 코드·자산 변경과 컴파일·메뉴·Play·Simulator·헤드셋·테스트·빌드 실행은 하지 않았다.

### 11.1 중간 — 두드림의 표면 방향 접근을 판정하지 않음

`KD1SurfacePractice.cs:158`의 이전 위치는 프레임 이동 120mm 초과를 거르는 데만 사용한다. `:167`~`:185`는 이탈 상태였는지와 현재 광선의 간격·법선·영역만 확인한다. 표면을 향한 이동이나 이전 접촉 간격에서의 접근은 확인하지 않는다.

가능한 사용자 경로: 작용 면을 장갑 위쪽으로 향하게 두고, 장갑 옆의 bounds 밖에서 작용 면 중심을 위쪽 표면과 거의 같은 높이로 유지한다. `:170`에서 이탈 상태가 성립한 뒤, 아래로 두드리지 않고 표면 위 12mm 이내 높이를 유지하며 옆으로 이동하면 광선이 처음 표면을 맞히는 순간 기록될 수 있다. 영역을 떠났다가 같은 방식으로 다른 영역에 진입할 수 있다. 즉 이탈 후 단순 근접 진입과 두드림을 구분하지 않는다. 정적 조건 분석이며 장치에서 재현하지 않았다.

보완 기준: 현재 프레임의 거리·방향뿐 아니라 유효한 표면 방향 접근을 확인한 접촉만 기록한다. 가로로 스치기·정지 상태의 방향 변경을 정상 두드림으로 대체하지 않는다. 깊이 초과 등 무효 경로 뒤의 접촉 기준도 검토하되, 임의의 강한 속도·충격량을 국군 정답으로 추가하지 않는다. 기존 접촉/이탈 허용오차와 추적 복귀 재기준화는 유지한다.

### 11.2 중간 — 착용 손 추적 소실 중에도 두드림 안내 유지

`KD1Equipment.cs:800`의 `IsReadyForSurface`와 `KD1SurfacePractice.cs:145`는 착용한 손의 추적 소실 시 진행을 멈추고 접촉 상태를 버린다. 그러나 `KD1Guide.cs:114`~`:118`은 잡고 있는 물체가 있을 때만 추적 안내를 선택한다. 착용 시에는 XRI 선택이 종료되어 GuidedItem이 없으므로 `:154`~`:158`에서 추적 여부와 무관하게 TapAreas/TapRemaining이 표시된다. `:87`~`:88`의 해제 보조 안내도 남는다.

영향: 손을 가려 추적이 끊기면 진행이 멈추지만 교육생은 계속 두드리라는 안내를 받는다. 보고서의 ‘연습 안내가 추적 안내를 가리지 않는다’는 설명은 착용 후 경로에는 적용되지 않는다.

보완 기준: 현재 연습에 쓰는 착용 손의 추적 소실을 화면 안내에 반영한다. 추적이 유효한 다른 손만으로 연습 가능한 경우까지 전역 차단하거나 양손 추적을 필수로 요구하지 않는다.

### 11.3 반영 확인·미확인 구분

- 기존 Pickup FBX의 `Glove_R_Pickup` 재사용, 인스턴스에서 다른 메시 숨김, 고정 장갑·3영역·표시·진행 연결은 구성 코드에 있다. 현재 메뉴 3은 미실행이므로 씬에 생성 완료로 기록하지 않는다.
- 작용 면 행렬, 왼손 미러 방향, 프레임당 1회·순서 55의 판정, 영역 중복 기록 방지, 추적/포커스 소실 시 접촉 상태 폐기 경로를 확인했다. 실제 감각·법선·배치와 UI 렌더링은 사용자 확인 대상이다.
- `EquipmentReset` 이벤트는 RestoreAll 뒤·VerifyInitial 앞에서 호출되어 기록과 접촉 상태를 초기화한다. 개봉·착용·해제의 일반 Version 변화에 기록 초기화를 연결하지 않는다.
- 화면의 겉봉투 명칭은 KD-1로 변경되어 있다. 메뉴 4는 읽기 전용 검사이며 정적 구성 통과와 동작 통과를 구분한다.
- Read/Write=false만으로 MeshCollider가 빌드에서 반드시 실패한다고 판단하지 않는다. [Unity 6.3 공식 문서](https://docs.unity.com/en-us/engine/6000.3/manual/physics-section/physics-overview/collision-section/collider-shapes/mesh-colliders/prepare-mesh-for-mesh-collider)는 비기본 cooking 설정·전단 변환·음수 축척의 convex 등에서 readable을 요구한다. 현재 새 구성은 고정 비볼록 Collider에 원본 메시를 연결하고 cooking 옵션을 별도 변경하지 않는다. 실제 빌드 동작은 미확인이며, 이를 이유로 원본 Importer를 먼저 변경하지 않는다.

다음은 위 두 보완의 처리 후 사용자 컴파일 → 기존 KD1 씬에서 메뉴 3 → 메뉴 2/4 → 좌우 한 손 정상 두드림과 가로 스침 비교 → 착용 손 추적 소실/복귀 → 초기화·재연습 확인이다. 이번 검토는 수정 프롬프트를 자동 제공하거나 코드를 직접 고치지 않았다.

## 12. 접근 기록·착용 손 추적 안내 수정본 재검토

사용자 수정 보고와 현재 SurfacePractice·Equipment·Guide·Editor Practice 코드를 대조했다. 코드·자산 수정이나 Unity·컴파일·메뉴·테스트 실행 없이 정적 검토했다.

### 12.1 반영 확인

- `KD1SurfacePractice.cs:204`·`:237`의 거리 기반 위치 기록과 CameIn은 현재 접촉 표면의 법선 기준으로 과거 위치와 현재 위치의 이동량·각도를 확인한다. 기록 경로에 높이 차이가 전혀 없는 가로 스침이나 위치 변화가 전혀 없는 회전은 이 조건 자체로 통과하지 않는다. 기록은 최대 64개이며 5mm 이상 이동 시 추가한다.
- `KD1Equipment.cs:810`의 IsHandTracked를 IsReadyForSurface와 Guide에서 함께 사용한다. `KD1Guide.cs:125`는 착용 손이 있으나 추적되는 착용 손이 없는 경우 Tracking을 표시한다. `:87`의 보조 해제 안내도 추적되는 착용 손이 있을 때만 표시한다. 반대 손 미착용·추적 소실을 전역 차단으로 추가하지 않았다.
- 메뉴 4에 minApproach·maxApproachAngle의 유한값·범위와 단위 출력이 추가됐다. 새 참조 연결은 없다. 새 접근 기록은 기존 DropContacts와 손 준비 무효·패드 변경·위치 점프·접촉 소비 경로에서 지운다.

### 12.2 중간 — 깊이 초과를 거절해도 접근 기록은 유지

`KD1SurfacePractice.cs:205`~`:207`은 `gap < -maxPenetration`인 경우 단순 return한다. 이때 state.apart와 path를 지우지 않는다. `:237`~`:246`의 CameIn은 path 안의 어느 과거 위치든 기준을 만족하면 통과하므로, 현재 움직임이 표면 밖으로 빠져나가는 중인지 확인하지 않는다.

기본값으로 가능한 정적 경로 예시(해당 부위 표면 법선 방향의 거리):

1. 표면 밖 +50mm에서 이탈 확인과 접근 기록이 생긴다.
2. 접촉 허용 구간을 프레임 사이에 건너뛰어 -20mm로 들어간다. 이동 70mm는 점프 기준 120mm보다 작다. 광선 시작점은 표면 밖 +10mm이므로 표면을 맞힐 수 있고, gap=-20mm가 침투 허용치 -15mm보다 깊어 거절된다. 하지만 접근 기록은 남는다.
3. -10mm로 빠져나오면 허용 접촉 범위 안이 된다. 과거 +50mm 위치와 현재 -10mm 사이의 60mm를 CameIn이 접근으로 인정하여 영역을 기록할 수 있다. 실제 마지막 움직임은 표면 밖으로 빠져나오는 방향이다.

이는 코드 조건을 대조한 경로이며 Unity 실행 재현은 아니다. 따라서 보고서의 ‘위치 점프·깊은 관통 후 빠져나오기 거절’ 중 위치 점프 폐기는 확인했으나 깊이 초과 처리까지 완료됐다고 볼 수 없다.

보완 기준은 깊이 초과 등 무효 관통이 관측되면 해당 시도의 이탈·접근 기준을 폐기하고, 충분한 재이탈 후 새 접근으로만 기록하는 것이다. 정상 접근 중 단순히 아직 멀다는 이유로 매 프레임 path를 지우는 변경은 피한다. 시간 제한·속도 기준 확대·씬 재제작을 우선 요구하지 않는다.

### 12.3 메뉴 3 안내의 적용 조건

현재 저장된 `B_KD1_Equipment.unity`에는 `KD1_GloveTarget`·`Progress` 및 practice/progressText 연결이 없다. 새 스크립트들의 meta도 아직 생성되지 않았다. 저장 파일 기준으로는 연습 구성을 아직 적용하지 않은 상태다. 사용자의 열려 있는 미저장 씬 상태는 확인하지 않았다.

이미 메뉴 3을 적용한 씬이라면 이번 설정값 추가만으로 메뉴 3을 다시 실행할 필요는 없다. 그러나 현재 저장본을 사용하는 경우에는 컴파일 후 메뉴 3의 최초 실행이 필요하고, 이후 메뉴 2·4를 검사해야 한다. 메뉴 1로 장면 전체를 재생성할 필요는 없다.

결론: 착용 손 추적 안내는 보완 반영, 접근 판정은 추가됐으나 무효 깊이 이후의 접근 기록 폐기 1건이 남는다. 코드 수정·실행 검증 없이 Docs/B만 갱신했다.

## 13. 사용자 판정 요구 완화 — 간단한 체험 우선

사용자는 ‘그 정도로 엄격한 판정은 필요 없으며 어디까지나 간단한 체험’이라고 명시했다. 따라서 §12의 깊이 초과 후 빠져나오기 구분은 필수 수정 요구에서 제외한다. 기존 코드가 그 경로를 차단했다고 기록하거나 실행 통과로 바꾸지는 않는다.

후속 설계·검토는 착용 패드의 작용 면이 표시 영역에 닿으면 수행으로 기록하는 간단한 체험을 우선한다. 같은 영역의 중복 집계 방지, 영역별 표시·완료, 한 손 조작, 추적/포커스 소실 중 새 기록 중단, 초기화는 유지할 기본 동작이다. 정교한 접근량·속도·깊이·궤적 구분을 추가 필수 조건으로 확대하지 않는다. 이미 구현된 접근 조건을 완화하는 코드는 아직 수정하지 않았으며, 수정 프롬프트는 사용자 명시 요청 때 채팅으로만 제공한다.

후속 사용자 확정: ‘각도는 계산에서 제외, KD-1 하단면이 닿았는지만 체크’한다. 착용한 제독 패드의 하단 작용 면 접촉을 성공 조건으로 삼고 각도·접근 방향·최소 접근량 검사는 제외한다. 윗면/옆면만의 접촉은 제외하되 하단 면이 실제로 닿는 동작은 허용한다. 기존 방향 광선의 각도 비교만 없애는 변경으로 완료 처리하지 않고 하단 면의 감지 범위를 기준으로 구현한다. 아직 코드에는 반영하지 않았다.

추가 사용자 피드백: 장갑 처리 표식이 처음부터 보이고 너무 작아 가시성이 낮다. 착용 중인 제독 패드가 있을 때만 표식을 표시하고, 크기·두께·중앙 표식을 확대하며 필요하면 별도의 최상단 표시 셰이더를 적용한다. 기존 코드는 Awake의 ShowMarkers와 URP Unlit LineRenderer를 사용한다. 패드 전체 해제 시 표시 숨김·수행 기록 유지, 재착용 시 상태 복원으로 연결한다. 표시 확대와 실제 접촉 범위가 어긋나지 않게 한다. 기존 `TQ_GuideMarker.shader`는 XR 대응 깊이 보정 방식으로 읽었으며 완전한 최상단 셰이더는 아니다. 기존 자산을 덮어쓰지 않고 KD1 전용 표시 자산을 구성하는 안을 제시한다. 이번에도 코드·셰이더·자산 수정과 실행 검증은 하지 않았다.

## 14. 하단 면 접촉·표식·공용 셰이더 수정본 검토

사용자 첨부 `72ee777c-d53f-40ab-8865-6cf1efcb2e87/붙여넣은 텍스트.txt`와 SurfacePractice·SurfaceZone·Guide·TrainingSubtitles·Editor Practice 및 새 공용 셰이더를 대조했다. 현재 씬과 KD1 표식 재질도 읽었다. 코드·자산·셰이더를 수정하거나 컴파일·메뉴·Play·Simulator·헤드셋·테스트·빌드를 실행하지 않았다.

### 14.1 실제 코드 반영

- `KD1SurfacePractice.cs:197`의 Sense는 IsReadyForSurface와 하단 센서 상자/영역 판의 겹침으로 기록한다. CameIn·각도 비교·접근 경로·접촉/이탈 재무장 조건은 제거됐다. Box.Overlap 안의 내적은 상자 교차 계산이며 제거 요청한 성공 각도 제한이 아니다.

- 안내 문구는 아랫면을 ‘대세요’로 바뀌었다. 기존 추적 안내와 한 손 흐름을 유지한다.

### 14.2 남은 실행 확인과 씬 반영

이번 수정 범위에서 추가 필수 수정 오류는 발견하지 못했다. 현재 저장된 KD1 씬의 세 영역은 radius=0.03이며 표식 재질도 기존 셰이더 참조를 유지한다. 이는 메뉴 3 갱신 전 상태이며, 코드 구현 완료와 씬 적용 완료를 구분한다. 사용자 미저장 씬이나 실제 동작을 확인한 것은 아니다.

## 15. 채움·외곽선·번호 표시 수정본 정적 검토

사용자 보고와 SurfaceZone·TrainingSubtitles·Editor Practice를 읽고 기존 SurfacePractice·공용 Overlay·저장 씬·재질 상태를 대조했다. 접촉 동작의 사용자 검증 완료는 유지하며, 이번 새 표시가 실제로 보인다는 확인으로 확대하지 않는다. 코드·자산 수정이나 Unity·컴파일·메뉴·테스트 실행은 하지 않았다.

## 16. 사용자 메뉴 3 실행 실패 — 95mm 자동 배치 제약

사용자가 메뉴 3의 실제 예외 로그를 제공했다. 재질 4개의 공용 Overlay·queue4000·색상 갱신 후, 가운데 glove-b를 유지한 상태에서 glove-a의 위치 검색이 실패했다. 스택은 `KD1EquipmentSetup.Practice.cs:355`의 FindUpperSurface 결과 null에 따른 예외다. 검토자는 메뉴를 재실행하지 않았다.

### 16.1 원인과 영향

- 코드가 영역 반경45mm 두 배와 여유5mm를 합한 중심 간격95mm를 자동 배치의 필수 조건으로 둔다.
- FindUpperSurface는 장갑의 긴 축을 따라 제한된 비율 후보에 위에서 아래로 광선을 쏜다. 폭 방향의 다른 위치는 탐색하지 않는다. 후보가 표면 법선Y≥0.6과 기존 중심과의95mm 거리까지 모두 만족해야 한다.
- 이번 실행에서 그 조건을 만족하는 glove-a 후보가 없어 예외가 발생했다. 이는 현재 후보 탐색의 실패이며 장갑 전체에 가능한 배치가 전혀 없다는 증거는 아니다.
- EnsureMarkers는 세 영역 배치가 끝난 뒤 호출되므로 이번 실패에서는 새 채움·번호 표식을 만드는 단계까지 도달하지 않았다. 재질 저장은 그 전에 수행되어 일부 갱신은 남을 수 있다. 현재 저장 씬에서 A/C 반경30mm, B45mm가 관찰된다. 이 중간 상태를 생성한 정확한 저장 경위는 추정하지 않는다.

### 16.2 수정 범위

수정 우선 대상은 Editor 메뉴 3의 영역 배치·기존 씬 갱신이다. 검증된 하단 접촉 알고리즘이나 새 셰이더, 장갑 모델을 먼저 수정하지 않는다. 메뉴 1 재생성이나 사용자의 장갑 수동 재배치를 우선 해결책으로 요구하지 않는다.

기존 영역이 있는 경우 표시 갱신을 불필요한 전면 재배치와 분리하는 방향을 검토한다. 확대·재배치가 필요한 경우 장갑 폭과 길이를 함께 탐색하고, 실제 표시/접촉 판의 겹침과 가독성을 기준으로 후보를 정한다. 일률적인95mm 중심선 검색 실패를 유일한 결론으로 쓰지 않는다. 모든 영역 후보를 확보한 뒤 적용하여 다음 실패로 크기·위치가 반만 갱신되는 일을 줄이고, 현재30/45/30 중간 상태에서도 반복 실행으로 복구할 수 있어야 한다.

현재 작업은 로그·코드·저장 씬 읽기와 Docs/B 갱신뿐이다. 수정 프롬프트는 사용자 명시 요청 시 채팅으로 제공하며 코드·씬·모델·재질을 직접 수정하거나 실행 검증하지 않았다.

사용자 보고와 현재 `KD1EquipmentSetup.Practice.cs` 및 기존 CanChange·상자 겹침 함수를 대조했다. 코드·자산 수정과 Unity·컴파일·메뉴·테스트 실행은 하지 않았다.

`KD1EquipmentSetup.Practice.cs:546`~`:547`의 Fill은 첫 유효 배치를 찾으면 즉시 true를 반환한다. 따라서 영역별 후보를 비용순 정렬했더라도, 같은 보존 조합 안에서 후보 비용 합이 가장 작은 전체 배치를 보장하지 않는다. `:499`는 각 보존 조합에서 처음 찾은 해끼리 비교한다.

현재 목적에서 추가로 반드시 고쳐야 한다고 확정할 코드 오류는 발견하지 못했다. 보고서의 최적 비용 보장 표현 1건은 정정 대상이다. 실제 장갑에서 유효 조합이 나오는지, 정상 갱신 후 재실행이 이동0인지, 실패 복구가 실제로 완료되는지는 아직 실행하지 않았다. 과거 실패 씬의30/45/30 상태가 저장 파일에 남아 있다.

## 18. KD-1 교육과정·메뉴 5/6 구현본 정적 검토

### 18.1 우선 보완 — 시작 대기 중 물리 이동을 초기 상태 이탈로 판단

### 18.2 보고와 일치한 구현

- 게이트 미지정 장비 씬의 기존 동작 유지, 새 입력만 차단하고 기존 선택을 강제로 취소하지 않는 경로가 반영됐다.
- 상태 관찰을 통한 4단계 신호, 회차 내 준비/착용 사실 유지, 연습의 실제 완료 상태와 Runner 완료 확인 후 한 번 생성하는 요약이 있다.
- 처음부터/다시하기는 하나의 TryReset을 통해 Runner 정지·사실/요약 삭제·기존 ResetEquipment·연습 초기 상태 확인·시작 화면 복귀를 수행한다.
- 기존 Guide의 행동/보조 안내는 GuideLines로 옮겨 교육 화면에서 재사용한다. 접촉 센서·표식·셰이더 변경은 이번 diff에 없다.
- 메뉴 5는 최초에 저장 장비 씬을 복사하며 재실행 시 교육 구성만 갱신한다. 메뉴 6은 읽기 전용 구성 검사다. 교육 데이터 자산 변경이 실패 복구 후 남을 수 있다는 로그도 있다.

### 18.3 범위와 다음 확인

현재 `Assets/B/Scene/B_KD1_Tutorial.unity`는 없다. 메뉴 코드 구현 완료와 씬 생성·컴파일·교육 실행 성공은 구분한다. 위 시작 준비 판정 보완 후 사용자 컴파일→메뉴5/6→시작 화면에서 잠시 기다려도 시작 가능 유지→좌우 각각 한 손 완주→다시하기 후 대기/두 번째 회차를 확인한다. 기존 접촉·메뉴3 검증 완료는 유지한다.

이미 보고된 초기화 실패 후 화면 내 재시도 없음과 장비 씬 변경의 교육 씬 자동 동기화 없음은 명시된 제한으로 유지하고 새 필수 확장 기능으로 배정하지 않는다. 다른 B 체험의 설명+행동 문구 정리는 KD-1 교육과정 완성 뒤, 공용 Overlay의 다른 씬 적용은 추후 통합 때 진행한다.

## 19. 시작 준비·복원 검사 분리 수정본 검토

사용자의 수정 보고와 Equipment/Course 실제 코드를 읽고 기존 호출부·씬/데이터 존재 여부를 확인했다. 코드·자산 수정·컴파일·Unity 실행은 하지 않았다.

- `KD1Equipment.cs:789`의 VerifyStoredState가 착용·선택·개봉·부모·표시·물리·수납 상태를 함께 검사한다. 자유 상태 KD-1의 정확한 위치/회전은 비교하지 않는다.
- `:774`의 VerifyInitial은 공통 검사 뒤에 기존 위치0.1mm·회전0.01도 기준을 유지한다. Awake:222와 ResetEquipment:714는 계속 이 검사를 쓴다.
- `:836`의 CheckReadyToStart는 CheckUsable과 VerifyStoredState만 호출한다. Course:272의 시작 준비 검사에서 사용하며 수행 기록0·표식숨김·요약없음·포커스 조건도 유지한다. 검사 중 위치나 상태를 바꾸는 처리는 없다.
- `:826`의 CheckRestored는 엄격한 VerifyInitial을 호출하며 Course:338의 초기화 직후 확인에 연결됐다. 이전 CheckStartState 참조는 없다.
- §18에서 지적한 정상 물리 안착을 초기 상태 이탈로 판단하는 경로는 코드상 보완됐다. 이번 수정 범위에서 추가 필수 코드 오류는 발견하지 못했다. 초기화 복원 검사 기준과 기존 장비 씬 동작은 유지된다. 실행 검증 완료를 뜻하지 않는다.

보고서의 적용 절차는 조건을 구분해야 한다. 이미 메뉴5로 만든 교육 씬이 있다면 이번 변경은 새 직렬화 참조가 없어 재실행할 필요가 없다. 그러나 현재 작업 폴더에는 `Assets/B/Scene/B_KD1_Tutorial.unity`와 `Assets/B/Data/Decontamination/KD1/KD1_Training.asset`이 모두 없다. 따라서 현재 상태에서는 사용자 컴파일→메뉴5 최초 생성→메뉴6이 필요하다. 메뉴1/3 재실행은 불필요하다.

다음 사용자 확인은 시작 화면5~10초 대기 후 시작 가능 유지, 한 손 전체 완주, 진행 중 처음부터/완료 후 다시하기 후 다시 대기 및 두 번째 회차다. 과거 메뉴3·접촉 사용자 검증은 유지한다.

## 20. 사용자 시작 직후 NotInitial 표시 보고

사용자가 수정본 실행 후 시작 직후 ‘장비가 처음 상태가 아닙니다’를 관찰했다. 현재 Tutorial 씬과 KD1_Training.asset 생성도 파일 존재로 확인했다. 코드와 기존 Editor.log를 읽었으며 실행을 대신하거나 코드를 수정하지 않았다.

- 현재 Course:272는 CheckReadyToStart를 사용하므로 이전 KD-1 루트0.1mm 위치 비교가 다시 시작에 사용되는 상태는 아니다.
- Course:273의 NotInitial은 장비 공통 검사 실패, 수행 기록 잔존, 표식 표시, 요약 잔존을 하나의 문구로 묶는다.
- Board:182가 TryCheckReady의 상세 out error를 버린다. 시작 버튼이 비활성화되므로 실제 시작 요청의 경고 로그도 발생하지 않는다. 읽은 최근 Editor.log에도 이번 준비 거절의 실제 조건이 없다. 화면 문구만으로 단일 원인을 확정할 수 없다.
- 조사 후보: Equipment:812~813의 수납물 로컬 위치0.01mm·회전0.01도 검사. 루트 검사와 별개로 남아 있지만 이번 증상의 원인이라고 재현/확인한 것은 아니다. 물리 부모 아래 kinematic 자식이라는 설명만으로 런타임 로컬 자세 불변을 보장했다고 단정하지 않는다.
- 우선 상세 실패 이유를 상태/이유 변경 시 한 번 출력해 실제 항목·예상값·실제값을 확보한다. 교육생 화면에는 개발용 상세를 노출하지 않는다. 그 결과로 논리 수납과 미세 자세 차이 문제인지 다른 상태 잔존인지 구분하여 최소 수정한다. 무조건 초기화·모든 조건 제거·메뉴1/3 재생성을 먼저 요구하지 않는다.

## 21. 슬롯·착용 위치 쓰기 수정과 사용자 1사이클 확인

사용자는 진단에서 Packet1의 슬롯 기준 +Y 0.8mm 이탈을 확인하고 PlaceInSlot/FitTo의 Rigidbody 위치 쓰기를 제거했다고 보고했다. 이어 1사이클 검증 성공과 현재 교육 UI/UX 만족을 명시했다. 실제 Item diff, Equipment 호출 경로, 준비 진단 코드와 기존 Editor.log를 읽었다. 검토자가 실행·컴파일하거나 프로젝트 코드를 수정한 것은 아니다.

### 21.1 코드와 기존 로그

- `KD1Item.cs:210`의 PlaceInSlot은 슬롯 부모·로컬 원점/항등회전·Stored 상태만 설정하며 SyncBody를 호출하지 않는다. `:219`의 FitTo도 HandFit 정렬 계산과 마운트 부모/로컬 자세 설정만 수행한다.
- Equipment의 슬롯 복귀·초기화는 기존 Apply 경로로 수납물의 kinematic/중력 꺼짐 상태를 적용한다. 착용도 선택 정상 취소→FitTo→Present 경로를 유지한다.
- 자유 KD-1 본체 초기화의 SyncBody(Equipment:755)와 벗은 패드의 SyncBody(:636)는 남아 있다. 위치 허용오차와 시작 준비/엄격 복원 검사 구분도 유지된다.
- 준비 진단은 Course.TryCheckReady 내부에서 안정된 항목/대상 key로 기록하므로 Board가 out error를 표시하지 않아도 콘솔에 원인이 남는다. 정상 복귀도 한 번 기록한다.
- 기존 Editor.log에서 수정 전 Packet1의 슬롯 위치 약(−0.0001,+0.8000,−0.0001)mm 및 허용오차0.010mm 실패를 확인했다. 이후 Run1 시작·4단계 진행·오른손 착용·3영역 수행·Runner 완료·요약 보관·장비 초기화·시작 대기 복귀 로그를 확인했다. 초기화 뒤 Focus 거절 로그는 앱 입력 포커스 조건이며 슬롯 위치 실패와 구분한다.
- 이번 수정 범위에서 추가 필수 코드 오류는 발견하지 못했다. 로그와 사용자 보고는 이번 실행에서 관찰된 위치 쓰기 충돌 해결과 한 회차 성공을 뒷받침한다. Unity 엔진의 모든 Rigidbody setter가 항상 같은 시점에 반영된다는 일반 명제로 확대하지 않는다.

### 21.2 검증 범위와 후속 UI 기준

사용자 1사이클 성공은 완료로 유지한다. 기존 로그의 초기화 복귀도 확인했으나 두 번째 회차 완료·좌우 각각 완주·HMD 양안/성능 전체 통과로 확대하지 않는다. 이미 성공한 한 회차를 다시 미검증 작업으로 배정하지 않는다. 메뉴 재실행은 이번 런타임 수정만으로 필요하지 않다.

사용자는 현재 KD-1 교육 UI/UX를 B 담당 전체 교육 UI의 기준으로 지정했다. 상단 챕터/단계 제목과 진행 박스, 목적·방법 설명, 현재 행동, 보조 안내·수행 수, 시작/완료·요약·다시하기 틀을 재사용한다. 각 과정의 단계 수·조건·용어는 해당 내용에 맞추며 전부 4단계로 강제하지 않는다. 설명+행동 문구 개선도 이 기준에 맞춘다. 다른 교육과정의 코드·씬을 이번 검토에서 일괄 수정한 것은 아니다. 공용 표식 Overlay의 다른 씬 적용은 별도로 합의한 추후 씬 통합 때 진행한다.
