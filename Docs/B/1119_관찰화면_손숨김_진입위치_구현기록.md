## 1. 관찰 카메라에서 기본 VR 손 숨김

### 새 런타임 컴포넌트
`Assets/B/Scripts/Interaction/ObserverHandHide.cs`(+`.meta`, guid `c13e1b1dd3fb4f7590750e043ef43b82`)를 추가했다.

- **어셈블리:** `MilTrainSimVR.B.Interaction`에 둔다. 참조는 기존 asmdef의 `Unity.XR.CoreUtils`(XROrigin)와 엔진 코어(`RenderPipelineManager`)만 쓴다.
  - ProtectiveClothing·K1 타입을 참조하지 않는다. asmdef 변경도 순환 참조도 없다.
- **직렬화 필드:**
  - `observerCameras`: 씬의 관찰 카메라 목록.
  - `baseHands`: 리그의 기본 손 Renderer 목록(C_ControllerHand_L/R).
- **동작:**
  - 관찰 카메라의 `beginCameraRendering`에서 각 기본 손의 `forceRenderingOff`를 보관하고 true로 바꾼다.
  - 같은 카메라의 `endCameraRendering`에서 보관한 값을 그대로 복원한다.
  - HMD와 그 밖의 카메라에서는 아무것도 바꾸지 않는다.
- **장갑 연계:**
  - `ProtectiveClothingUserBody`는 기본 손 숨김을 LateUpdate(40)와 `onBeforeRender`에서만 정한다. 카메라별 콜백에서는 손을 건드리지 않는다.
  - 그래서 관찰 카메라 직전에 보관하는 값이 곧 장갑 정책의 값이다. 장갑을 착용한 손은 복원 후에도 숨은 채로 남고, 맨손은 HMD에서 다시 보인다.
  - false로 강제하는 경로는 없다. 장갑과 착용 기록은 읽지도 쓰지도 않는다.
- **카메라 순서:**
  - 보관과 복원이 카메라 한 대 단위로 짝을 이루므로 렌더 순서와 무관하다.
  - end가 오지 않은 경우도 처리한다. 다음 비관찰 카메라의 begin이나 다음 프레임 LateUpdate(기본 순서 0으로 UserBody 40보다 앞)에서 먼저 복원한다. 관찰 카메라가 연달아 오면 처음 보관한 값을 유지한다.
- **처리 주체:**
  - static owner는 로드된 전체 씬에서 하나다. 두 번째 인스턴스는 오류를 내고 렌더 이벤트를 구독하지 않는다(컴포넌트 enabled 자체를 false로 바꾸지는 않는다). 현재 CourseRoute는 LoadSceneMode.Single로 전환하며 각 대상 씬의 인스턴스는 1개다.
  - 여러 거울은 같은 컴포넌트의 카메라 목록으로 처리한다.
  - `RuntimeInitializeOnLoadMethod`로 도메인 리로드를 생략한 Play에서도 owner를 초기화한다.
- **정리:** `OnDisable`(비활성화, 씬 언로드)에서 구독을 해제하고 남은 임시 숨김을 복원한다.
- **검증 (`TryValidate`):** 실패하면 숨기지 않는다. 기본 손은 관찰 화면에도 보이는 안전한 쪽으로 남는다.
  - 카메라와 손 목록이 비었거나 null이 있으면 실패.
  - 같은 항목이 중복되면 실패.
  - `MainCamera` 태그 카메라(HMD)이면 실패.
  - 카메라가 손의 XROrigin 아래에 있으면 실패.
- **건드리지 않는 것:** 손 루트, 컨트롤러 루트, Interactor, 추적, 손가락 포즈. 꺼지는 것은 Renderer의 렌더링 플래그뿐이다.

### 기존 카메라별 숨김과의 관계
B_CBRN의 `TrainingFieldCoordinator`도 같은 begin/end 방식으로 다른 스테이션의 사용자 몸 Renderer를 관찰 카메라에서 숨긴다.

- 그 Renderer는 스테이션의 `userBodyRenderers`(마네킹·착용 메시·K1 아바타)다. 기본 손과 겹치지 않으므로 두 처리는 서로 덮어쓰지 않는다.
- Coordinator의 스테이션 관찰 카메라 목록은 이번 연결과 같은 세 카메라다.

## 2. 화생방·구급법 진입 위치

| 씬 | EntryAnchor (Transform fileID) | 이전 | 이후 | 회전·축척 |
|---|---|---|---|---|
| B_CBRN | 1261173846 | (0, 0, −0.85) | **(0, 0, −1.85)** | Y 180°, (1,1,1) 유지 |
| B_FirstAid | 1220096312 | (0, 0, −0.85) | **(0, 0, −1.85)** | Y 180°, (1,1,1) 유지 |

- **진입 처리:** `TrainingFieldCoordinator`가 앵커의 world 위치와 forward를 읽는다.
  - 초기 임시 배치: `SetPositionAndRotation(entryAnchor…)`.
  - 추적 후 `PlaceAtEntry`: `MatchOriginUpCameraForward` + `MoveCameraToWorldLocation`.
  - 따라서 앵커만 바꾸면 된다. XR Origin 저장 위치 (0,0,−2.5)와 진입 준비·추적 대기·입력 복구 흐름은 그대로다.
- **변경하지 않은 것:** ExitAnchor, 포털의 위치·회전·축척·판정·전환 코드(포털 local Z −0.116 / −0.223 포함), 허브 쪽 배치, 다른 튜토리얼 씬.

### 함께 이동하는 자식 (주의)
- EntryAnchor의 자식 `Entrance_Stand`(입구 안내판: 교육 목록·안내 문구)는 앵커를 따라 1 m 함께 이동한다.
- world (−1.2, 0, −1.40)에서 **(−1.2, 0, −2.40)**으로 간다.
- 사용자 기준 위치(앞쪽 0.55 m, 왼쪽 1.2 m)는 그대로다.
- 지시가 EntryAnchor만 바꾸라고 했으므로 안내판 local 값은 보정하지 않았다.
- 안내판을 문 앞 원래 world 위치에 남기려면 `Entrance_Stand` local Z를 1 m 보정해야 한다(앵커가 Y 180°이므로 local Z −1.0).
  - 이는 사용자가 결정할 사항이며 이번에는 적용하지 않았다.

### 배치 정적 확인 (저장값 계산, 실측 아님)
- **방:** `B_BarracksShell` 내부(x −4.0 ~ 4.0, 북벽 z ≈ 0, 남벽 z ≈ −9.44). 바닥 `Shell/Floor`는 z 0 ~ −9.44 범위이며, 새 지점 (0, −1.85)는 이 바닥 위 중앙 통로 x 범위(−0.75 ~ 0.75)에 있다. 주변 반경 1 m 안에 벽, 작업대, 스테이션 물체는 없다.
- **스테이션 실습 범위(LocalArea를 world로 환산):**
  - B_CBRN K1: x −4.0 ~ −2.16, z −5.30 ~ −2.40
  - B_CBRN 보호의: x 1.85 ~ 4.0, z −5.07 ~ −1.70
  - B_FirstAid 지혈대: x −4.0 ~ −2.65, z −4.25 ~ −1.60
  - B_FirstAid 압박붕대: x 2.9 ~ 4.0, z −4.07 ~ −1.05
  - 새 진입점과의 x 간격은 최소 1.85 m다. 이동한 안내판과의 간격은 K1 0.96 m, 지혈대 1.45 m다. 겹침은 없다.
- **순간이동 목적지:** 새 지점은 Walk_Entry(z ≥ −1.20)와 Walk_Centre(z ≤ −2.60) 사이에 있다. x = 0이 EntryRight(x 0.25 ~ 0.90) 밖이므로, 순간이동 목적지 사각형 밖에서 시작한다.
  - Walk_*는 TeleportationArea의 목적지 충돌체일 뿐 서 있는 위치를 제한하지 않는다. 바닥 위이므로 충돌 근거로 보지 않았다.
  - 시작한 자리로 다시 순간이동할 수는 없다. 목적지 사각형은 바꾸지 않았다.
- **포털 뒤 여유:** 지시서의 계산값(0.33–0.35 m → 1.33–1.35 m)을 기준으로 삼았고 이번에 다시 계산하지 않았다. 앵커만 −Z로 1 m 이동하므로 여유는 1 m 늘어난다.

## 5. 미검증

- 모든 실행 결과: URP와 XR 단일 패스에서 관찰 카메라 begin/end 순서와 HMD 렌더가 기대대로 분리되는지.
- 기본 손이 숨은 관찰 화면에서 컨트롤러 위치를 알아보기 어려운지 등의 사용성.
- 안내판이 1 m 이동한 결과가 의도에 맞는지, 그리고 원래 위치에 남길지에 대한 결정.
- 시작 자리가 순간이동 목적지 밖이어서 생기는 사용성 영향.
- 포털 뒤 여유의 실측.

## 6. 보고서·실제 코드·씬 후속 정적 검토

2026-11-19 사용자 요청으로 `ObserverHandHide.cs`·기존 렌더 표시 처리·씬 파일·진입 흐름을 읽기 대조했다. 컴파일러·Unity·Play·Simulator·테스트·빌드는 실행하지 않았다. 이번 후속은 이 기록과 Docs/B/AGENTS.md만 수정하고 코드·씬·설정은 보존했다.

### 6.1 확인 결과

- 네 대상 씬마다 새 컴포넌트가 1개다. 새 Transform은 SceneRoots에 등록돼 있고 파일 내부 ID 중복은 발견하지 못했다.
- `observerCameras`는 실제 거울/후면 컴포넌트의 viewCamera 집합과 일치한다. B_CBRN 3개, 보호의 각 씬 1개, B_K1_Tutorial 2개 모두 Camera 타입의 유효한 내부 참조다. HMD는 목록에 없다.
- 기본 손은 각 씬 리그의 좌우 SkinnedMeshRenderer를 참조한다. 원본 fileID는 L 7035100983345267098 / R 5303875590615372752이며 마네킹·장갑은 이 목록에 없다. K1 씬의 새 stripped Renderer 참조도 같은 공통 리그 인스턴스를 가리킨다.
- 현재 `TrainingFieldStation.userBodyRenderers`와 기본 손 목록의 교집합은 없다. 기존 Coordinator의 다른 스테이션 숨김 처리와 새 기본 손 숨김은 대상이 분리돼 있다.
- 일반 카메라 순차 렌더 흐름에서 begin이 기존 플래그를 보관하고 end가 복원한다. 무조건 false로 만드는 경로는 없다. UserBody의 기존 기본 손 정책은 LateUpdate/OnBeforeRender에서 결정되고 카메라별 SetHmdView는 기본 손을 쓰지 않으므로 현재 코드상 장갑 상태를 덮어쓰는 경로는 발견하지 못했다. 실제 URP/XR 렌더 결과는 미확인이다.
- OnDisable은 구독을 해제하고 남은 임시 숨김을 복원한다. 실제 전환 경로인 CourseRoute의 Single 씬 로드와 현재 씬별 구성에서 추가 확정 오류는 발견하지 못했다.
- 두 EntryAnchor는 정확히 (0,0,-1.85), Y 180도, 축척 1이며 부모가 없는 루트다. 기존 PlaceAtEntry가 앵커의 월드 위치·방향을 사용하므로 1m 전진 의도와 일치한다. 포털 원본·ExitAnchor·기존 local Z 배치는 이번 변경에 포함되지 않는다.
- 현재 포털 world Z는 화생방 -0.206, 구급법 -0.184다. 진입 상자 깊이 0.9 × 축척 0.7의 반깊이는 0.315m이므로 새 시작점과 가까운 판정 경계의 Z 간격은 각각 1.329m / 1.351m다. 머리 높이·실제 이동을 포함한 실측은 아니다.

### 6.2 문제 판단과 사용성 항목

**추가 필수 수정 오류는 미발견이다.** 컴파일·VR 렌더링·손 복원·씬 왕복의 실제 통과를 의미하지 않는다.

1. `Entrance_Stand` 동반 이동은 사실이다. 진입한 사용자와 안내판의 상대 배치를 유지하므로 현재 요구에서 원위치 복원을 필수로 볼 근거는 없다. 안내판의 최종 배치 선호는 사용자 관찰로 확인한다.
2. 새 시작점이 Walk_* 목적지 밖인 점도 사실이다. 이 영역은 순간이동 착지 대상이며 일반 바닥 위 시작 자체를 금지하지 않는다. 다만 정확히 그 자리로 순간이동해 돌아올 수 없는 사용성 제약은 남는다. 시작점을 순간이동 목적지로도 제공하려는 경우에만 별도 영역 보정을 검토한다.
3. 보고서의 ‘두 번째 컴포넌트가 꺼짐’은 ‘이벤트를 구독하지 않아 숨김 기능이 동작하지 않음’으로 명확히 했다. 현재 네 씬에는 각각 1개뿐이므로 중복 상태로 인한 실제 결함은 발견하지 못했다.

사용자 우선 확인은 ① HMD/거울/후면 화면의 손 표시 구분 ② 왼쪽 장갑만 착용 후 초기화 시 기본 손 복원 ③ 화생방·구급법 진입 후 0.5m 후진과 의도적 포털 복귀 ④ 씬 왕복이다. 기존 §4의 입력·기대 결과·실패 기준을 사용한다.
